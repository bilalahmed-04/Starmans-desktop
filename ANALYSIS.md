## 1. PROJECT OVERVIEW

This is a **billing and inventory management web app** for a shoe-sole manufacturing/trading business. Internally the design docs call it "Soleria Sole House," but the shipped app currently displays the brand as **"Starmans / Starmans Sole House"** (the rename was never applied to the running app).

In plain terms, it lets a small sole-manufacturing shop:
- Sell sole products to clients and generate numbered invoices ("slips")
- Track stock levels per article (sole type/color/size)
- Log daily production, which adds to stock
- Record operating expenses, utility bills, and chemical purchases/usage
- Record payments received from clients
- View profit/loss reports (monthly, annual, and a pie-chart analytics view)

It is a **single-admin app** — one login, no multi-user roles, no accounts-receivable ledger (payments are informational only).

Originally the app was designed to run with **zero backend** (a single self-contained HTML file with in-memory JS state, per `Project_detials/Soleria - Project Overview.md`). That design has since been **superseded**: a real Express + MongoDB backend was added, and the React frontend was fully wired to it via a fetch-based API layer. The `Project_detials/*.md` docs describe the *original, no-backend* vision and are now historical/aspirational rather than a description of the current app.

## 2. TECH STACK

**Backend** (`Backend/`)
- Node.js (ESM, `"type": "module"`) + **Express 4**
- **MongoDB** via **Mongoose** (`mongoose: ^9.7.3`)
- **JWT** auth (`jsonwebtoken`) — Bearer token
- **bcryptjs** — password hashing
- **express-rate-limit** — brute-force protection on login
- `cors`, `dotenv`
- Dev reload via `node --watch`

**Frontend** (`frontend/app/`)
- **React 19** + **TypeScript** + **Vite 7**
- **Tailwind CSS** + shadcn/ui primitives (Radix UI components under `src/components/ui/`) — mostly scaffolded but **not actually used**; pages are hand-styled with custom CSS classes instead
- `react-router` / `react-router-dom` are installed but **unused** — navigation is done via a reducer + string state, not real routes
- `recharts`, `three` (used by a `Ballpit` background component), `lucide-react` icons, `sonner` (toasts), `zod` + `react-hook-form` (mostly unused/scaffolded), `date-fns`

**Database**: MongoDB (Atlas in practice, per project status notes). No SQL.

**No test suite** is configured in either backend or frontend.

## 4. HOW IT WORKS

**Backend flow** (`Backend/src/index.js` is the entry point):
1. Loads env vars (`dotenv`), connects to MongoDB (`connectDB()` in `db.js`).
2. Registers Express middleware: `cors()`, `express.json()`.
3. Mounts one router per resource under a path prefix (`/auth`, `/articles`, `/clients`, `/slips`, `/productions`, `/expenses`, `/bills`, `/chemicals`, `/payments`, `/profit`).
4. Every router **except** `/auth/login` and `/health` is protected by `requireAuth` (JWT Bearer check, see `middleware/auth.js`).
5. Falls back to a 404 JSON handler, then a generic error handler.
6. Listens on `process.env.PORT || 5000`.

Data access is plain Mongoose model calls inside each route file (no service/repo layer). Business logic lives directly in the routes — e.g. `routes/slips.js` does client de-duplication (matches by phone, prompts on name mismatch via a `phone_conflict` 409), stock validation/deduction on sale, and stock restoration on slip edit/delete.

**Frontend flow**:
1. `main.tsx` renders `<AppProvider>` (global state) wrapping `<App/>`.
2. `AppContext.tsx` initializes state from a JWT stored in `localStorage` (`starmans_token`). If a token exists, the user is considered logged in and the app starts on `home`; otherwise it starts on `login`.
3. On login (`isLoggedIn` becomes true), a `useEffect` in `AppContext` fires parallel fetches for articles, clients, productions, expenses, bills, chemical purchases/usage, and payments via `src/lib/*.ts` helpers, all of which call `apiRequest()` in `lib/api.ts` (adds the `Authorization: Bearer <token>` header, points at `VITE_API_URL` or `http://localhost:5000`).
4. **Routing is not URL-based.** `App.tsx` reads `state.currentPage` (a plain string) and does prefix matching (`page.startsWith('slips')`, etc.) to decide which page component to render. Navigation is just `dispatch({ type: 'NAVIGATE', page })`.
5. Each page component manages its own sub-view state (tabs like Daily/Weekly/Monthly) internally and calls the relevant `lib/*.ts` functions directly for CRUD, which then re-fetch and `dispatch` updated lists into the global store.
6. Stock is never edited directly — it's mutated server-side as a side effect of Slip create/update/delete and Production create (see `routes/slips.js` `checkAndDeductStock` / `restoreStock`).

## 6. SETUP STEPS

Two servers must run concurrently: the backend API (port 5000) and the frontend dev server (port 3000).

### Backend
```bash
cd Backend
npm install
cp .env.example .env   # NOTE: no .env.example currently exists in the repo — you'll need to create .env manually (see below)
npm run dev             # node --watch src/index.js, http://localhost:5000
```
Required `.env` variables (inferred from code, not committed to the repo):
```
MONGODB_URI=mongodb://localhost:27017/starmans   # or an Atlas URI
JWT_SECRET=<any secret string>                    # required — requireAuth will throw without it
JWT_EXPIRES_IN=7d                                 # optional, defaults to 7d
PORT=5000                                         # optional, defaults to 5000
```
Then seed the database once:
```bash
npm run seed   # wipes and re-populates all collections with demo data (admin/admin login)
```

### Frontend
```bash
cd frontend/app
npm install
npm run dev      # Vite dev server, http://localhost:3000
```
Optional `.env` (Vite) variable:
```
VITE_API_URL=http://localhost:5000   # defaults to this if unset
```

### Login
Seeded credentials are `admin` / `admin` — **but** per the project status notes, the live dev database credentials had been changed to `bilal` / `12345678` via the Settings page at last check. If login with `admin`/`admin` fails after seeding fresh, that's expected/correct; re-run `npm run seed` to reset to `admin`/`admin`.

## 8. IMPORTANT NOTES

- **`frontend/app/CLAUDE.md` is stale.** It states "All data is currently in-memory demo data... there is no backend/API integration yet," which was true at some earlier point but is **no longer accurate** — `src/lib/*.ts` and `AppContext.tsx` now fetch everything from the live backend API. Trust `Project_detials/Project Status - 2026-07-17.md` over `CLAUDE.md` for current architecture state.
- **`Project_detials/Soleria - Project Overview.md` describes a different, earlier architecture** (single self-contained HTML file, zero backend, "Design Component" runtime). That vision was superseded by the current Express+MongoDB+React setup — treat that doc as product/UX reference (module descriptions, business rules, formulas) rather than a technical description of the current codebase.
- **Navigation is not real routing.** There are no URLs per page — refreshing the browser always drops you back to whatever `currentPage` computes to from the stored JWT (`home` if logged in, `login` if not). Don't expect `/slips/123`-style deep links to work.
- **Stock is derived, never directly editable.** It only changes via Production entries (increase) and Slip create/update/delete (decrease/restore). This is intentional (see `Soleria - Project Overview.md` §7) to prevent data corruption — if you're debugging a stock discrepancy, look at `routes/slips.js` (`checkAndDeductStock`/`restoreStock`) and `routes/productions.js`, not a direct stock-edit endpoint (none exists).
- **Client identity is phone-based, not name-based**, in `routes/slips.js`: a new slip looks up an existing client primarily by phone number, and if the name doesn't match, the API returns a `409 phone_conflict` requiring the frontend to explicitly resolve via `clientResolution: 'existing' | 'new'`. This two-step conflict flow is easy to miss if you only skim the happy path.
- **Discounts are per line item**, and can be either `'%'` (percentage) or `'Rs'` (flat rupee amount) — never both — computed in `calcItemAmount()` in `routes/slips.js`.
- **Login is rate-limited** at 5 failed attempts per 15 minutes per IP (`routes/auth.js`); successful logins don't count against the limit. This can make repeated local testing with a wrong password lock you out for 15 minutes.
- **Currency is Pakistani Rupees (₨)**, formatted with `toLocaleString('en-US')` — this is a Pakistan-market-specific app (client examples are Pakistani business names, phone number formats are `03XX-XXXXXXX`).
- **Dark mode exists** and is persisted via `localStorage`, toggled from the header — added per `Project_detials/Claude Code Prompt - Frontend Changes.md`, along with a Home dashboard page, animated login background, and animated donut charts on the Profit → Analytics tab.
